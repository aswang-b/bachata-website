# src/pages/admin Context

> Tier 3 — referenced from [docs-overview.md](../../../docs/ai-context/docs-overview.md). Secondary admin pages, linked from the main dashboard at `src/pages/admin.astro` (a sibling file, not in this directory).

## Purpose

Each file is a standalone Astro page gated by `requireAdmin`-style client checks, rendered per request (`prerender = false`, so the header and footer follow the live settings; never cached at the edge), heavy on inline `<script>` (no framework components in this project — see [components CONTEXT.md](../../components/CONTEXT.md)). All fetch their data from the matching route under [`src/pages/api/admin/`](../api/admin/_CONTEXT.md).

## Key Files

| File | Purpose |
| --- | --- |
| `analytics.astro` | "Dashboard" page (`/admin/analytics`, titled "Dancer Dashboard"), linked from `admin.astro`. Sortable/filterable tables for Sign-Ups (Drop-Ins show their chosen class date, editable per registration), Event Registration (event sign-ups only, kept out of Sign-Ups and Attendance since nobody checks in to events; Paid checkbox, edit (dancer details, payment, or switching events) and delete to the Recycling Bin, all under its own edit lock), Check-Ins, and Attendance (matches + orphan workqueue; orphaned check-ins can be linked to a class date), the last driven client-side by `attendanceMatching.ts`'s matching over data from `attendance-data.ts`; Each tab's "Filter by class" takes several [class] [date] rows (`classFilterGroup.ts`, "+" adds a row) and shows rows matching any of them. The Recycling Bin marks auto-detected duplicate submissions with a "Duplicate" badge. Below lg (phones, tablets) every `table.card-table` shows as compact rows (the `<style is:global>` at the end): a paid dot (`data-card-dot`) or attendance mark (`data-card-status`: ✓ ✗ –), the name (`data-card-title`) followed by any `data-card-inline` columns (`="end"` at the line's right, e.g. Event Registration's Paid switch), then one line of the fields picked in the collapsed "Fields on each row" picker (defaults: `data-card-default`; remembered per table in localStorage), ending in the action icons (`data-card-actions`; `="top"` puts them on the first line, as in the one-line Recycling Bin rows). Paid boxes everywhere are `.paid-toggle` switches (✗ / ✓). An orphan's Resolve cell (`data-card-panel`) shows only in the opened row, unlabelled; its buttons are pills in rows (Link; Create Check-In + Mark No-Show; Delete). A row is held open only by text boxes (an edit row), not by dropdowns; open rows stay open through a redraw (sort, lock heartbeat), found again by their cells' text. Saved row fields are keyed by column (`data-column`). Sort buttons below lg skip columns marked `data-card-nosort` (contact, phone, email, payment, type of registration); desktop headers still sort by every column. Tapping a row opens every column, labelled; a dancer's extra classes (`data-card-continued`) add their own line to the same box. A MutationObserver re-marks the cells after each render. Large file (~1,850 lines) — mostly inline table-rendering/sort/filter script |
| `qr.astro` | Door Signs (`/admin/qr`; `/admin/checkin-qr` forwards here). Saved signs: cards with their classes (one per line), Venmo account, short link, scans this week (bars) and branded-code status; Open (full screen), Download (PNG named for the heading), Edit, Delete. The editor: pick classes (optionally also register attendees as drop-ins), a Venmo account (remembered, someone looked up, or none) and a heading; before saving it shows a plain code for the pick, after saving the sign's own short link and branded code. A new sign's link without a branded code gets one at once: the QR site's generator, embedded in a dialog (iframe; only messages from its origin and that iframe are read), makes it and spares; a banner offers the same for any others, and another remakes codes still in standard colours as vivid (`remake`). If no ticket can be made, the full-page generator, coming back with `?qr_ids`. On the sign: "Check in", and "Haven't paid yet?" over the Venmo code with the account's Venmo name. Full screen sizes the codes to fit the class names (`--note-lines`); one code at a time on a phone; screen kept awake. Venmo accounts tab: default, remove. API: `qr-studio.ts` |
| `feedback.astro` | Feedback requests (`/admin/feedback`, from the General tab). Requests tab: pick a class date, whole series or event (who came is listed to tick) or type in a class name and dancers, choose a questionnaire, change its opening message for this request; each request's card shows results by question, the link anyone can use and one-tap WhatsApp buttons. Questionnaires tab: the builder (`lib/feedbackBuilder.ts`) with a preview for a sample, or for a chosen class and one of its dancers. Which dancer gave which answer is never shown |
| `notifications.astro` | Push notifications (`/admin/notifications`, from the General tab, and the calendar editor's Notify link with `?event=<id>`). How many devices get them (under the heading); a message (title, text, the page it opens) with a preview, filled in from a chosen class or event; Send asks first, and asks again for an event already sent about; the history with reached, shown, opened (and the open rate), failed and removed counts, a Continue button on a send that stopped partway, and, on a finished send only, a trash can that removes it from the history (after asking; an offline failure says so and can be retried). API: `push.ts` |
| `inbox.astro` | Contact-form submission inbox (`inbox-data.ts`), marks-as-seen backing the unread badge in `Header.astro` (`unseen-count.ts`) |

## Integration Points

- **Depends on**: `src/pages/api/admin/*` (all data), `src/lib/attendanceMatching.ts` and `src/lib/classSeries.ts` (client-side matching/occurrence logic in `analytics.astro`)
- **Used by**: linked from `src/pages/admin.astro`'s header and from `src/components/Header.astro`'s admin nav

## Architecture

Every page here links back to `/admin` (the main dashboard) rather than nesting a shared admin layout — navigation is a manual back-link, not a route-group layout.
